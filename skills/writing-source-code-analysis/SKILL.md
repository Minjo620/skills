# 源码解析写作

## 核心原则

以最低的认知成本，帮助目标读者建立与源码一致、可以核查的系统心智模型。研究方法保持稳定，叙事结构随系统和读者变化，语言风格由作者确认。

## 工作流

1. **识别任务**：区分研究、文章设计、撰写、改写和审校；判断对应的 Diátaxis 文档类型。架构、生命周期和设计权衡通常采用解释型文档（Explanation），但不得强行套用。
2. **建立文章配置**：读取 [作者确认与文章配置](references/author-brief.md)。从用户要求和仓库中推导可确认项，只询问会实质改变文章的未决项。长篇公开文章在设计大纲前确认仍未解决的高影响选择；用户明确要求直接执行时，说明必要假设并继续。只读研究可以先进行。
3. **研究源码**：读取 [源码研究与证据方法](references/research-method.md)。先验证入口、调用关系、数据与状态变化、持久化、异常路径和测试，再设计文章结构。内部保留证据索引。
4. **选择叙事**：需要设计或重构文章结构时，读取 [叙事模式](references/narrative-patterns.md)。尚未确定主线时，研究完成后提出 2—3 种适配方案，说明认知主线、优缺点和风险并给出推荐；用户已经选定结构时，验证它与源码是否匹配，只在存在冲突时提出调整。研究、改写和审校任务不需要强制生成备选方案。
5. **统一术语**：在写大纲前建立「源码名称 → 中文统一名称 → 定义与边界」映射。同一概念不得轮换近义词；关系尚未验证时不得凭字面翻译。
6. **设计与撰写**：每节承担一个主要认知任务，先给整体关系，再解释局部机制。按照作者确认的交付节奏完成；逐章确认不是默认要求，而是文章配置。
7. **语言审校**：写作和改写时读取 [中文书写规范](references/chinese-style.md)。Humanizer 只能润色和精简，不能删除关键机制、条件和边界。
8. **完成核查**：发布或交付前读取 [审校清单](references/review-checklist.md)，分别检查技术事实、叙事、术语和格式。

## 输出约定

- 公开正文与内部研究材料分离；源码路径、行号、commit 和代码片段是否公开，由文章配置决定。
- 正文说明系统做什么、为何这样协作、状态怎样变化、边界在哪里；源码证据支撑结论，不替代解释。
- 细节是否进入正文，取决于它是否改变行为、边界或工程判断，而不是它位于代码的哪一层。
- 段落可以承担事实、因果、边界、例证或必要过渡；精简不等于删除所有连接句。

## 常见错误

| 错误 | 修正 |
| --- | --- |
| 研究前套用固定章节 | 先验证系统，再选择叙事主线 |
| 按目录逐个介绍文件 | 按生命周期、数据流或设计问题组织 |
| 提前翻译源码术语 | 先验证所有权、基数和生命周期 |
| 为避免重复轮换概念名称 | 维护统一术语表 |
| 把推断写成设计意图 | 明确事实、推断和观点的确定性 |
| 以最短篇幅为目标 | 以最低认知成本为目标 |
