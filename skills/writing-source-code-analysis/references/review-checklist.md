# 源码解析文章审校清单

## 技术核查

- [ ] 已记录分析范围和源码状态。
- [ ] 每项重要结论都有内部证据索引。
- [ ] 功能入口有真实调用方，不只是存在定义。
- [ ] 配置项已经追踪到读取和生效位置。
- [ ] 数据的写入、保存、读取和最终使用已经闭环。
- [ ] 正常路径之外检查了失败、重试、并发、恢复和清理。
- [ ] 测试验证的行为没有被扩大解释。
- [ ] Prompt 约束没有被写成模型行为保证。
- [ ] 源码事实、官方说明、工程推断和作者观点可以区分。
- [ ] 无法确认的问题保持未知，没有用合理猜测补齐。

## 叙事核查

- [ ] 文章解决了配置卡中的核心认知问题。
- [ ] 开头建立必要的整体心智模型，没有过早堆术语。
- [ ] 章节按真实机制组织，而不是按目录或固定模板组织。
- [ ] 每章只有一个主要认知任务，子问题与主线相关。
- [ ] 关键因果、状态变化和系统边界没有因精简而丢失。
- [ ] 图、表、列表和代码比连续文字更适合对应信息。
- [ ] 结尾形成判断或边界收束，没有机械复述全文。

## 术语与语言核查

- [ ] 陌生概念在首次出现时已经解释。
- [ ] 中文概念在前，英文或源码名称在后。
- [ ] 同一概念全文名称一致，没有近义词轮换。
- [ ] 相近源码对象没有被错误合并。
- [ ] 标题具体、准确，没有含糊代词和未经定义的比喻。
- [ ] 删除了研究记录、澄清过程、宣传语言和重复总结。
- [ ] 中英文空格、大小写、直角引号和代码格式一致。

## 苏格拉底式自审

这些问题用于内部审校，不要机械写进正文：

1. 这一节结束后，读者应该准确理解什么？
2. 每一段防止了哪种误解，或者建立了哪条因果关系？
3. 删除这句话会损失事实、边界、例证还是必要过渡吗？
4. 这个细节是否改变系统行为或工程判断？
5. 这个术语是否已经由源码关系验证？
6. 这个设计动机是证据、推断，还是作者评价？
7. 是否存在更简单但仍然准确的表达？

发现问题时直接修订正文，不在成稿中保留审校对话。
