# 中文源码解析文章书写规范

## 第一原则

准确性、概念一致性和可理解性高于语言变化。精简的目标是降低认知成本，不是追求最少字数。

## 术语

- 首次出现采用「中文概念（英文名或源码名称）」：任务运行记录（rollout）、候选结果（`raw_result`）。
- 先解释概念在系统中的作用，再给出源码名称；不得先抛术语，数段之后才定义。
- 之后优先使用统一的中文名称。需要对应源码或区分相近对象时，再重复英文名。
- 同一实体、状态或机制使用同一名称，不为避免重复而轮换近义词。
- 源码中多个相近词不得凭字面合并。通过创建者、所有者、基数、生命周期和读写路径确定关系。
- 作者归纳的中文概念只有在准确映射实现、定义清楚并能降低理解成本时使用。

## 段落与标题

- 每节承担一个主要认知任务；每段承担事实、因果、边界、例证或必要过渡中的一种主要功能。
- 先给结论或关系，再补充理解该结论所需的机制。
- 标题准确描述内容，不使用含糊代词、未经定义的比喻、营销语言或刻意口语化表达。
- 删除写作过程，例如「这里需要澄清」「我们先来看」「值得注意的是」。确有逻辑作用时改写成直接陈述。
- 允许必要的阶段结论和章节过渡；删除只换一种说法复述前文的总结。

## 中文格式

- 中文与英文、阿拉伯数字之间留空格，例如「系统发起 8 个请求」。
- 保留产品名和技术名的正确大小写，例如 iPhone、Wi-Fi、SQLite、Web Search。
- 使用直角引号「」；引号内再次引用时使用『』。
- 文件名、字段名、配置项、命令和代码标识使用反引号。
- 中文标点前后不额外添加空格。

## 表达形式

- 连续因果关系使用自然段。
- 并列条件使用列表。
- 固定维度比较使用表格。
- 生命周期和调用顺序使用流程图或时序图。
- 层级与文件职责使用目录树。
- 代码片段只保留解释机制所需的部分，并立即说明它证明了什么。

## 语言审校

使用 Humanizer 或其他润色方法时，只处理重复、僵硬句式、空泛修饰和编辑痕迹。不能省略输入条件、状态变化、失败路径、权限边界和必要术语定义。
