# 作者确认与文章配置

## 目的

文章配置记录会改变内容选择和叙事方向的决定。先从用户请求和现有材料中填充，不要要求作者重复已经提供的信息。

## 决策原则

- 能从源码确认的事实由研究解决，不向作者提问。
- 只询问存在多种合理选择、且不同答案会明显改变成稿的问题。
- 一次最多提出 1—3 个简短问题；提供推荐选项及其影响。
- 用户要求直接开始时，列出必要假设并继续；不要用问卷阻断任务。
- 长篇公开文章在大纲或正文写作前，至少确认目标读者、文章任务和证据展示方式。

## 文章配置卡

| 字段 | 需要确定的内容 |
| --- | --- |
| 文章任务 | 解释型文档（Explanation）、教程（Tutorial）、操作指南（How-to）、参考文档（Reference），或明确的混合边界 |
| 目标读者 | 已知知识、无需掌握的知识、阅读动机 |
| 核心承诺 | 读完后能够理解、判断或完成什么 |
| 技术深度 | 架构、生命周期、调用链、语言细节、性能或历史的侧重 |
| 证据展示 | 正文是否出现路径、符号、行号、commit、代码片段和外部链接 |
| 语言与平台 | 语气、篇幅、排版规范、发布平台 |
| 交付节奏 | 一次完成、先大纲、逐章确认或研究报告后再写 |
| 特殊边界 | 隐私、保密、本地文件、禁止操作和不可公开信息 |

## 默认配置

当作者没有指定，而且不会造成高风险偏差时，可采用以下默认值：

- 面向具备领域基础、但未研究过当前实现的技术读者；
- 架构和机制解析采用 Diátaxis 的解释型文档（Explanation）；
- 先研究，后提出叙事方案和大纲；
- 正文以机制为主，证据索引内部保留；
- 实现语言细节只在影响机制时展开；
- 使用自然、准确、克制的中文。

这些是可覆盖的默认值，不是所有文章的硬规则。

## 作者确认格式

不要发送长问卷。先用一小段话总结已经确认的内容，再提出当前最关键的未决问题。例如：

> 我已经确认文章面向有并发基础的开发者，目标是解释调度器的运行机制，正文不展示行号。现在唯一会改变大纲的问题是：你希望主线围绕「一次任务如何运行」，还是围绕「调度器的组件关系」？我推荐前者，因为它更容易建立端到端心智模型。
