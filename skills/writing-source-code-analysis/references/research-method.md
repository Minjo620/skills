# 源码研究与证据方法

## 研究目标

源码研究不是收集文件简介，而是建立能够支持文章结论的证据链。先回答系统如何运行，再解释为什么这种设计成立。

## 开始时记录

- 远程地址、分支、commit、最近提交和工作区状态；
- 用户允许的读取、执行和公开范围；
- 目标子系统及其相邻边界。

这些信息默认进入内部研究记录。是否写入公开文章由文章配置决定。

## 研究顺序

1. **确定边界**：找到功能入口、启动条件、配置读取和关闭路径。
2. **识别对象**：确认核心类型、所有权、包含关系、生命周期和持久化载体。
3. **追踪主路径**：从输入到输出记录每一步修改的对象和状态。
4. **追踪读取路径**：确认保存的数据是否真的被读取、何时读取，以及是否进入最终消费者。
5. **检查异常路径**：覆盖失败、重试、取消、并发、恢复、清理和过期。
6. **交叉验证**：检查调用方、单元测试、集成测试、配置 Schema、Prompt、数据库查询、仓库文档和 Git 历史。
7. **寻找反证**：主动寻找绕过条件、未接入配置、仅有定义却没有调用的代码，以及与注释冲突的行为。

## 证据优先级

| 类型 | 能够支持的结论 |
| --- | --- |
| 实现与真实调用链 | 当前行为和数据流 |
| 行为测试 | 预期边界和回归约束 |
| 配置读取与 Schema | 配置是否存在、如何生效 |
| 数据库结构与查询 | 状态、选择、排序和恢复行为 |
| Prompt | 模型被要求做什么，不能单独证明模型一定做到 |
| 注释与仓库文档 | 官方说明和研究线索 |
| Git 历史、PR、Issue | 设计演化和动机证据 |

不要仅凭名称、注释、README 或配置项推断实际行为。

## 持久证据台账

长篇、多阶段或跨会话研究不能只把证据索引留在对话上下文中。开始大规模研究前，确认一个后续阶段可以重新读取的 Markdown 台账。短答、局部审校等单轮任务可以不落盘。

### 存储位置

按以下顺序选择，未经授权不得为了建立台账修改被分析的源码仓库：

1. **文章工作目录**：首选 `<文章工作目录>/.source-analysis/evidence-index.md`，让研究材料与文章共用生命周期，同时与公开正文分离。
2. **用户级私有状态目录**：没有文章工作目录、源码仓库只读或证据包含内部信息时，使用 Agent 可访问的用户级状态目录，例如 `~/.local/state/source-code-analysis/<repository-id>/<task-id>/evidence-index.md`。
3. **源码仓库内的本地目录**：只有用户明确允许时，才使用 `<源码仓库>/.source-analysis/evidence-index.md`；确保它不会被误提交。

不要把任务台账保存在 Skill 安装目录。Skill 更新和任务研究具有不同的生命周期。若用户只授权读取，又没有可用的私有状态目录或持久 Artifact，应先说明限制，不得擅自写入源码仓库。

### 记录格式

每项准备影响文章结论的重要判断记录：

| 字段 | 内容 |
| --- | --- |
| 编号 | 稳定且唯一的结论编号 |
| 结论 | 准备写入文章的具体判断 |
| 证据 | 文件、符号、行号、测试或历史记录 |
| 调用关系 | 定义由谁调用，在哪些条件下执行 |
| 反证检查 | 是否存在绕过、例外或冲突行为 |
| 结论类型 | 源码事实、官方说明、工程推断、作者观点 |
| 置信度 | 已确认、有限确认、无法确认 |
| 状态 | 有效、已修订或已撤销 |
| 公开方式 | 正文、脚注、附录或仅内部保留 |

### 更新与重载

- 结论被确认、修订或撤销，或者证据、置信度和适用范围发生变化时，立即更新台账；不要记录所有搜索过程和临时观察。
- 写大纲、正文和最终审校前重新读取台账，不得只凭上下文中的印象重建证据。
- 多个 Agent 参与研究时，由一个协调者维护主台账；其他 Agent 返回结构化证据，避免并发改写同一文件。
- 台账默认只供内部研究使用。优先记录相对路径，并按安全边界处理用户名、本地绝对路径和私人数据。

## 表达确定性

- 「源码实现了」「测试验证了」用于直接证据。
- 「从调用关系可以推断」用于证据充分但没有明确契约的判断。
- 「可能」「尚无法确认」用于证据不足的解释。
- 作者评价必须说明评价依据和替代方案，不伪装成维护者意图。

## 安全边界

- 不修改、删除或还原用户已有文件，除非任务明确授权。
- 不公开密钥、账号、用户内容、本地绝对路径或私人持久化数据。
- 检查本地状态时只记录结构和经过脱敏的行为证据。
